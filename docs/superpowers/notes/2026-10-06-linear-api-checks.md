# Linear API 실측 (1부)

- 날짜: 2026-10-07
- 커밋: 5b64a01 (feat/part1-core-cli, 최종 리뷰 수정 반영 후)
- 방법: 실제 워크스페이스(팀 3개)에서 release 바이너리와, 키를 0600 임시 헤더 파일로 넘기는 읽기 전용 curl 쿼리로 확인. 이 문서에는 이슈 제목, 사람 이름, 워크스페이스 정보를 남기지 않는다.

| 확인 항목 (스펙 15장) | 결과 | 비고 |
|---|---|---|
| `issues(orderBy: updatedAt)` 정렬 방향 | 해당 없음 | 로컬에서 항상 다시 정렬하므로 결과에 영향 없음 |
| `containsIgnoreCase`가 한글에서 동작하는가 | 동작함 | 빈 캐시에서 한글 한 단어 검색 시 서버 결과 여러 건. 두 단어 AND 검색도 맞게 걸러짐 |
| `issue(id:)`가 보관 이슈를 어떻게 돌려주는가 | `archivedAt`을 채워서 돌려줌 (not found 오류 아님) | 휴지통 이슈는 `archivedAt`과 `trashed: true`가 함께 옴. CLI는 둘 다 "보관되었거나 삭제된 이슈예요"로 안내 |
| 50건 페이지 복잡도 (`X-Complexity`) | 16 (실제 소모 15점) | `x-ratelimit-complexity-remaining` 차이로 실측. 문서 공식 추정치(약 1,800점)보다 훨씬 낮음 → `labels(first: 20)` 유지. viewer 쿼리는 68 |
| 깊은 검색(코멘트 포함) | 동작함 | 코멘트에만 있는 단어: 일반 검색 0건, `--deep` 1건 |
| 오프라인 동작 | 동작함 | `HTTPS_PROXY=http://127.0.0.1:9`로 연결 실패를 흉내 냄(ureq가 프록시 환경 변수를 따름). `mine`, `search`, `show`는 저장된 결과와 "(오프라인: …)" 안내를 보여줌. 본 적 없는 이슈는 명확한 오류 |
| markdown 렌더링 (제목·목록·코드·표·이미지) | 동작함 | 인용, 링크 번호 `[n]`, 이미지 자리 표시와 URL 목록, 표(넘치는 셀은 `…`), 코드 블록 들여쓰기와 줄바꿈을 실제 이슈로 확인. 공백 없는 긴 URL은 글자 단위로 줄이 바뀌지만 `[n]` 목록에 전체 URL이 있음 |

## 추가 확인 (최종 리뷰 권고)

| 항목 | 결과 | 2부·3부 설계에 주는 의미 |
|---|---|---|
| 코멘트 기본 정렬 (`comments(first:)`, orderBy 없음) | **최신순(내림차순)** | `first: 50`은 최신 50개를 준다. 상세 화면은 이를 시간순으로 다시 정렬해 보여주고, "더 있어요"는 그보다 오래된 코멘트를 뜻한다 |
| 한도 헤더 종류 | `x-ratelimit-requests-{limit,remaining,reset}`, `x-ratelimit-complexity-{limit,remaining,reset}`, `x-complexity` | `searchIssues` 성공 응답에도 엔드포인트별 헤더는 없었다. 엔드포인트 한도(분당 30회)에 걸렸을 때의 헤더는 아직 확인하지 못했다(리뷰 M9 유지) |

## 그 밖에 본 것

- 요청 한도는 시간당 2,500회이고, CLI 명령 하나에 요청 1~2회를 쓴다.
- 워크스페이스 상태 이름에 이모지가 들어갈 수 있다(예: "✅ Done"). 표시에는 문제가 없다.
