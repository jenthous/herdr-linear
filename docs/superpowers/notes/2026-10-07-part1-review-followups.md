# 1부 최종 리뷰 후속 항목

1부(코어 + 조회 CLI) 최종 리뷰에서 Critical 1건과 Important 2건은 고쳤다. 아래는 일부러 미룬 항목과, 실행 중에 내린 결정 가운데 2부·3부 계획에 영향을 주는 것이다. 2부 계획을 쓸 때 입력으로 쓴다.

## 고친 것 (참고)

| 항목 | 내용 | 커밋 |
|---|---|---|
| C1 | `&#27;` 같은 문자 참조가 파싱 뒤 제어 문자가 되어 sanitize를 우회 → 렌더링 결과(span, 링크 URL·라벨)를 출력 직전에 다시 거름 | ffcc9a3 |
| I1 | 빈 캐시 파일 동시 생성 경합, 비원자적 초기화 → WAL 전환 재시도, IMMEDIATE 트랜잭션 안에서 버전 재확인 후 `IF NOT EXISTS`로 생성, 캐시를 못 열면 메모리 캐시로 계속 | 8cfba8b |
| I2 | 키를 바꿔도 60분 동안 이전 워크스페이스 정보를 씀 → viewer 캐시를 키 지문과 묶고, `mine`·`show`도 먼저 워크스페이스 확인 | 5b64a01 |

## 미룬 Minor (2부·3부에서 처리)

| 번호 | 내용 | 처리 시점 제안 |
|---|---|---|
| M1 | `cache.retention_days`에 아주 큰 값이면 i64 overflow (debug 패닉, release는 매번 캐시 삭제) → 상한 또는 `saturating_mul` | 2부 (설정 읽기를 다시 볼 때) |
| M2 | `whoami`·`login` 문구와 `main`의 오류 출력에 sanitize 미적용 (팀·워크스페이스 이름, 서버 오류 메시지) | 2부 (TUI의 모든 표시 문자열에 같은 원칙 적용) |
| M3 | 표 셀 안 링크·이미지에 번호와 URL이 없음 | 2부 (상세 화면 `u` 목록) |
| M4 | 검색어의 nucleo 특수 문법(`!`, `^`)이 해석됨 → 단어마다 `AtomKind::Fuzzy` 리터럴 atom | 2부 (타이핑 검색) |
| M5 | 로컬 순위의 AND 의미가 서버와 다름 (단어가 제목·본문에 나뉘면 0건, 번호 일치가 나머지 단어 무시) | 2부 (타이핑 검색) |
| M6 | `teams` 설정 오타면 범위가 전체로 넓어짐 → 일치하는 팀이 0개면 경고 | 2부 |
| M7 | env 키 인증 실패 문구가 스펙 10장 문구와 다름 | 2부 (키 입력 화면) |
| M8 | 한도 초과·인증 오류 때 저장된 결과로 대신하지 않음 | 2부 (SWR 화면) |
| M9 | "n분 후"가 requests 헤더 기준이라 엔드포인트 한도(`searchIssues` 분당 30회)에 걸리면 틀릴 수 있음. 실측해 보니 성공 응답에는 엔드포인트 헤더가 없었음 | 2부 (깊은 검색 안내) |
| M10 | client 타임아웃 테스트 없음 | 2부 |
| 권고5 | 식별자 강조가 `UTF-8`, `SHA-256`, `ISO-8601`도 강조 → 알려진 팀 키로 제한 | 2부 (상세 화면) |

## 2부·3부로 넘긴 결정

- 로그 파일(`herdr-linear.log`, 1MB 회전): 장기 실행 TUI가 생기는 2부에서 넣는다.
- 패닉 훅과 터미널 복구: 2부 TUI에서 넣는다(`ratatui::init`이 패닉 훅을 설치함).
- `RateLimit::should_pause_auto` 연결: 자동 요청(사이드 패널 주기 새로고침, 서버 검색 디바운스)이 생기는 2부·3부에서 연결한다.
- 결과를 합칠 때 선택 유지: TUI 상태라 2부에서 구현한다.
- 연 뒤 읽기 중 `SQLITE_CORRUPT`: 장기 실행 프로세스에서 캐시를 다시 만드는 처리를 2부에서 본다.
- 화면 외형(코드 블록 배경이 글자에만 칠해짐, 목록·인용 안 표의 접두사 손실, 번호 목록 체크박스의 번호 손실): 2부 화면 작업에서 판단한다.
- `NO_COLOR`, broken pipe 패닉: 필요하면 2부에서 함께 처리한다.
